# Scope of poise

Date: 2026-11-25. Issue: #5. Decided by the maintainer; this record was written with an AI assistant.

## Question

Can a soft robot body be used as part of the computation for its own control?

This is called **physical reservoir computing**. A body with many coupled, elastic parts reacts to its
inputs in a rich, fading way: its present state still carries traces of recent inputs. If that state is
measured, a simple trained readout (here, a linear one) can turn it into useful outputs, and the body
itself does the rest of the computation without being trained.

Within the [Physical-Edge Native Architecture](https://physical-edge-native.github.io/), this is one way a
body or medium can act as a computing component (decision of 2026-11-25 in
[pena-meta](https://github.com/physical-edge-native/pena-meta)). Dyne, the project's first implementation,
keeps producing an inspectable model of a space; poise explores the other case, where the physical system
is used directly and is not modelled.

## Decision

### Bodies, in order

1. **A mass-spring network**: point masses joined by springs and dampers, driven by inputs at some of the
   masses. It is the classic model of a physical reservoir with a compliant body
   (Hauser et al., 2011, "Towards a theoretical foundation for morphological computation with compliant
   bodies", *Biological Cybernetics*). It is used first to settle the tasks, the measurements and the
   comparison, while everything is small and easy to inspect.
2. **A soft arm**: a continuum arm, like the silicone arm inspired by an octopus that has been used as a
   physical reservoir (Nakajima et al., 2015, "Information processing via physical soft body",
   *Scientific Reports*). It is closer to a robot and is the step towards control.

### Simulators

- The mass-spring network is written in this repository in plain **NumPy**, so that every step is visible
  and the simulation is deterministic.
- The soft arm uses the soft-body features of **MuJoCo**, the simulator erg uses. Both run on CPUs; no GPU
  is assumed.

### What is trained

Only a **linear readout** from the measured state of the body is trained. The body itself (its shape,
springs, materials) is not trained or optimised.

### Comparison

Every result with a body is compared with **the same linear readout applied to the inputs alone, without a
body**. This is the lower bound: the difference shows what the body contributes. Both use the same inputs,
the same tasks, the same training data and the same way of fitting the readout.

Added 2026-11-26 (#11, after reviewing prior work): the same readout is also applied to **a window of
past inputs** (a tapped delay line, with and without polynomial features). With only the current input,
any body with memory wins memory tasks almost by construction; the delayed-input baseline shows how many
past inputs the body is worth and separates memory from nonlinearity (#12). Information processing
capacity is measured for the same reason (#13).

poise makes no claim that a physical reservoir is better than other approaches. The measured differences,
including tasks where the body does not help, are the result.

### Dependency on Dyne

poise does **not** depend on Dyne for now and pins no commit of it. Running the readout with Dyne's
learned-solver component, so that it gives the same bits on a PC and on a microcontroller, may be decided in
a later issue.

### Checks

A simulation gives the same result for the same seed on the same machine, and the tests check this. Whether
results are also bit for bit the same across operating systems, or need a stated tolerance and its reason,
is decided in the issue that adds the first simulation.

### A second fixed body for reference

Added 2026-11-26 (#11): besides poise's own network, a network with the settings of Hauser et al.
(2011) may be measured once with the same tasks and baselines (#14), to separate differences due to the
network from differences due to the task definitions. It is taken from the paper, not chosen by its
scores, so the body is still not optimised.

## Not covered for now

These may be added later by a new decision:

- hardware (building a soft body and measuring it with real sensors);
- training or optimising the body itself;
- comparison with a rigid body of the same shape;
- comparison with a reservoir that exists only in software (for example an echo state network) or with a
  small trained neural network policy.

## Options considered

First body:

- (a) Mass-spring network first, then a soft arm. **Chosen**: the tasks and measurements are settled on a
  small model that is cheap on CPUs, before the harder soft body.
- (b) Start directly with a soft arm. Closer to a robot, but the tasks and the measurements would be
  settled at the same time as the hardest simulation.
- (c) A soft legged or crawling body. Closer to erg, but the design of the body and of the control would
  both be hard at once.

Simulator:

- (a) Own NumPy code for the mass-spring network, then MuJoCo for the soft arm. **Chosen**.
- (b) MuJoCo from the start. One tool, but harder to compare with the classic mass-spring results.
- (c) A simulator specialised for soft bodies (such as SOFA). More accurate, but heavy and hard to run in
  CI on Linux, macOS and Windows.

Comparison (several could be chosen):

- inputs alone, without a body. **Chosen**.
- a reservoir in software (echo state network) with the same readout size. Not chosen for now.
- a rigid body of the same shape. Not chosen for now.
- a small trained neural network policy with the same training budget. Not chosen for now.

Dyne:

- (a) No dependency for now. **Chosen**: the first work is the simulation and the measurements.
- (b) Run the readout with Dyne's learned-solver component from the start, pinning Dyne as a submodule.
